## Classification rubric

Each row has exactly one classification from the audit brief:

- `WORKING`: production-reachable implementation exists and repository tests or direct code paths substantiate the claimed behavior.
- `PARTIALLY_WORKING`: a useful implementation exists, but a material scope, trust, reliability, or integration gap remains.
- `MOCKED`: the user-visible result comes from deterministic mock data or a mock service.
- `HARDCODED`: the behavior/data is fixed in source rather than derived from user or service state.
- `PREVIEW_ONLY`: reachable only from SwiftUI preview infrastructure.
- `DEBUG_ONLY`: compiled or selected only in Debug.
- `TEST_ONLY`: exists only to support tests/evaluations.
- `BROKEN`: code is reachable, but its behavior materially contradicts the feature contract.
- `DEAD_CODE`: implementation exists but no production call path uses it.
- `NOT_IMPLEMENTED`: no substantive implementation exists.
- `CANNOT_VERIFY`: repository evidence is insufficient without runtime, deployment, hardware, or account access.

Launch priority uses `P0` for trust/core-loop/public-launch blockers, `P1` for useful beta, `P2` for launch polish, and `P3` for intentionally deferred expansion. `—` means maintain the existing behavior.

## Executive truth

The truthful production core is narrower than the UI suggests. Typed or spoken text can enter a real local-parser → geocoder → backend GraphHopper pipeline, and real loop generation, route-quality checks, maps, persistence, voice transcription, and route thumbnails have substantial implementation and tests. However, the release UI also exposes a parallel mock product: example chips, the “Continue outside” recent route, the Explore catalog, and “Edit with AI” all surface fabricated route data or transformations. `TrailRoute` has no provenance field, so those routes can be displayed and saved as if they were verified live routes. Removing or unmistakably isolating those paths is the first launch requirement.

Runtime/build execution is reported separately in `BUILD_AND_RUNTIME_REPORT.md`; rows that require an actual launch, production deployment, or physical-device App Attest verification remain conservative here.

## Highest-priority conclusions

1. **P0 — Remove release-reachable mock routes and mock route editing.** Example chips, Home history, Explore, and AI editing can all produce or preserve fabricated route facts.
2. **P0 — Add route provenance.** The model/persistence/UI cannot distinguish GraphHopper output from `MockRoutes`, so a mock can be saved indefinitely as if verified.
3. **P0 — Stop preference-as-fact difficulty labels.** Requested “easy” currently replaces computed difficulty.
4. **P0 — Fail closed on backend intent configuration.** The no-provider path is an ungated deterministic mock labeled `remoteAI`.
5. **P0 — Verify production infrastructure on a real device.** Backend routing, durable App Attest storage, entitlement environment, and route sessions are substantial but not yet proven end to end by repository evidence.

## Documentation contradictions exposed by the code

- `AGENTS.md`/`PROJECT_CONTEXT.md` describe mock fallback routes as a current foundation and tell agents not to break them, while also requiring that route geometry/stats never be invented. Production reachability makes those rules incompatible; mocks must be isolated to Preview/Debug/tests.
- `PROJECT_CONTEXT.md` says no backend and no AI integration, but a Node backend, Google/OpenRouter intent parsing, GraphHopper proxy, App Attest, PostgreSQL persistence, and an iOS backend gateway now exist.
- `PROJECT_CONTEXT.md` says SwiftData is planned; the current saved-route feature is already implemented through a versioned JSON file store.
- Product copy suggests nearby personalization, conditions, water/exposure context, practical stops, AI route editing, and route start/navigation beyond the verified implementation.
