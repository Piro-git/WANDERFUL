## Decision

The existing App Attest PostgreSQL pool can hold a short atomic transaction in both the long-lived service and Vercel's handler. Weather uses that **same app-security pool**, rather than a new service or a per-process cache. A separate reviewed SQL migration is required because the phase-1-v2 bootstrap migration set and its admission inventory are intentionally frozen. This patch does not edit or silently append to that ledger. If the deployment owner cannot approve and apply the separate migration in the selected database, the feature stays off.

A single `route_weather_control` row serializes **new provider admissions** across all instances. Admissions start at least 600 ms apart using database time. At most two admissions fit in any one-second interval; even if every allowed same-origin redirect produces a second HTTP request, that remains at most four provider requests per second, conservatively below MET's 20 requests/second application-wide agreement threshold. The control row also applies a 60-second backoff after 429 and a 10-second backoff after other failures. These are not per-process counters.

Each rounded coordinate has a durable JSONB document, `Expires`, verbatim `Last-Modified`, and a 12-second owner-token lease. The transaction commits **before** HTTP. Other instances wait up to six seconds for the same coordinate, then return unavailable if no fresh fill appears. A crashed worker's lease expires; a late worker cannot overwrite a newer lease. A 304 extends expiry only when an old document exists. Fresh entries are never evicted early; at the 128-entry cap expired, unleased entries can be reclaimed. If full of fresh entries, the preview becomes unavailable. This cap is **a closed pilot limit, not public-load capacity**. Database/timeout/provider failure never returns an expired forecast as fresh and never blocks the route itself.

The provider receives only validated route sample latitude/longitude, truncated to at most four decimals. It receives no prompt, account ID or device IP. Each provider request is bounded to one HTTPS origin, one same-origin redirect, 5 seconds and 256 KB of decompressed response. Route previews still reject stale model updates and incomplete three-sample coverage. The server now constructs the real provider only with a durable store; `ROUTE_WEATHER_ENABLED=true` without the pool or migration fails closed. The iOS flag and all tracked defaults remain false.

## Capacity decision and pilot stop limits

128 fresh coordinate entries can serve at most **42 complete routes with three disjoint samples** before the 43rd route becomes unavailable; overlap improves this, but no overlap is guaranteed. MET's [Terms](https://api.met.no/doc/TermsOfService) and [Locationforecast HOWTO](https://docs.api.met.no/doc/locationforecast/HowTO.html) require keeping a response through its actual `Expires` and revalidating later with the original `Last-Modified`. We must not evict fresh entries merely to admit new coordinates. MET does not promise a fixed cache lifetime or compact-response byte size. The 8-timeseries synthetic fixture is only 1,383 bytes minified and cannot establish a realistic live size. No live response was fetched here.

The adapter accepts at most 256,000 decompressed bytes per response, and the SQL limits the stored JSON text to 256,000 bytes. Payload-only planning scenarios for 128 entries are 8,192,000 bytes at 64 KB each, 16,384,000 at 128 KB, and **32,768,000 bytes** at the admission ceiling. PostgreSQL row/index/TOAST overhead, dead tuples and WAL are additional; none of these scenarios is a measured live MET distribution or a hard bound on `pg_database_size`. Raising the cap to 256 would double the maximum accepted payloads to 65,536,000 bytes before overhead and is unjustified without a fresh capacity proof.

The existing staging-only Supabase Free capacity contract sets a 400,000,000-byte settled operating target and records 355,657,472 bytes for active plus superseded regional generations. Its remaining target headroom is **44,342,528 bytes**. Reserving a **50,000,000-byte weather planning envelope** (32,768,000 payload + 17,232,000 for physical overhead/growth) would put that historical state at 405,657,472 bytes, over the target. This is not the selected live database measurement. Supabase currently documents a 500 MB Free database-size threshold with read-only behavior above it; database size includes data and indexes and differs from disk/WAL. [Capacity contract](../../backend/config/outdoor-capacity-profiles/supabase-free-bounded-two-core-v1/capacity-contract-v1.json), [Supabase database-size docs](https://supabase.com/docs/guides/platform/database-size).

For a **Free-plan closed pilot only**, require a current `pg_database_size(current_database()) <= 350000000` **before** migration/activation, leaving the 50 MB planning envelope below the project's 400 MB operating target. The 17,232,000-byte overhead allowance is a planning reserve, not a measured bound; actual PostgreSQL relation size must be watched. After activation, query every 10 seconds during the bounded pilot:

```sql
SELECT (SELECT count(*) FROM trailmind_app.route_weather_cache) AS entries,
       (SELECT count(*) FROM trailmind_app.route_weather_cache
         WHERE expires_at > clock_timestamp()) AS fresh_entries,
       pg_total_relation_size('trailmind_app.route_weather_cache')
         + pg_total_relation_size('trailmind_app.route_weather_control') AS weather_relation_bytes,
       pg_database_size(current_database()) AS database_bytes;
```

Warn and stop expanding the pilot at **96 fresh entries** (75% of the cap). Disable the server flag at **120 fresh entries**, **40,000,000 weather relation bytes**, or **380,000,000 database bytes**, whichever comes first. At the maximum admission pace, the 32-entry reserve between 96 and 128 can disappear in about 19 seconds; a 10-second sample interval leaves limited operator response time, so automation or a very small supervised pilot is required. The thresholds are operating stops, not guarantees about physical storage. If the selected database starts above 350 MB or cannot be monitored at this cadence, leave weather off. Do not enable weather publicly at 128 entries without representative same-database peak occupancy evidence below 96 and a renewed database/TOAST/bloat capacity proof; otherwise design a larger proven store or capacity plan. No paid plan is authorized by this handoff.

## Integration review — admission blocker (2026-09-30)

**Do not apply this migration to a selected deployment yet, even with weather disabled.** The existing `APP_ATTEST_RUNTIME_PRIVILEGE_MANIFEST` lists only the six App Attest tables. Its exact admission query in `stagingDatabaseAdmission.js` rejects runtime privileges on any other application relation. The proposed weather grants therefore fail the existing service admission check. A separately reviewed manifest/admission version or isolated weather-role design is required before migration; this integration deliberately does not broaden that frozen contract. The local component race test does not prove whole-service startup compatibility.

The integrator reproduced another preflight defect with disposable PostgreSQL: the service pool's admitted `pg_catalog,trailmind_app,pg_temp` path makes `current_schema()` return `pg_catalog`, so the original preflight incorrectly returned false. The preflight now checks that exact normalized path and verifies both unqualified weather relations resolve to the intended schema. This remains only a weather-component check; a `ready = t` row cannot override the full service-admission blocker above. No cloud migration was run.

## Remaining boundaries

This verifies the SQL and concurrency semantics locally, not the selected cloud role topology, cloud database latency, Vercel pool capacity, MET availability, deployment fleet membership, or a live forecast. PostgreSQL errors may spend up to the existing five-second app-security query timeout before showing unavailable. A waiting caller can spend up to six seconds on a coordinate; three sequential sample calls remain within the existing HTTP request bound under normal database behavior. A lost worker can delay same-coordinate recovery for 12 seconds. Stale forecast data is never shown as fresh. No promise of weather safety or complete route coverage is added.
