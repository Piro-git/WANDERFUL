# Bounded research lifecycle diagnostic proposal

This directory contains reviewed diagnostic preparation and a research-only protocol candidate. Fixtures establish request and refusal behavior; publication does not establish actual provider completion, an active entitlement or live phone acceptance. Ordinary `backend/package.json` and `backend/vercel.json` remain unchanged.

## Code rules

One explicitly selected operator action can reserve at most one Google diagnostic attempt. The proposed native phase is separate: at most one intent/plan, eight Google and six GraphHopper attempts. Original cumulative provider ceilings remain 16 and 10. Every attempt, including failure or revision, counts.

The proposal generator requires literal counter preconditions 2/6/0 and prior supplement values 1/1/2/0, no active lease, no existing sequence-2 entitlement and the same active key. These are code/test parameters, not a report of actual accounting state. Diagnostic source, approval digest, key, origin and deadline are bound before reservation. Diagnostic expiry is at most ten minutes; a later native binding is one-time and at most thirty minutes. It cannot reset or replace prior spent accounting.

RLS, role/column permissions, enabled invoker guards, fixed search paths, revoked-key/owner checks and native lease authentication remain required. Charges update the typed phase and original cumulative counters together. Replay or racing operator execution fails at reservation before another Fetch.

## Explicit operator selection

`prepareOperatorDiagnostic.mjs` generates an insert-only SQL proposal and public binding parameters. It performs no database, cloud or provider action.

`vercel.operator-diagnostic.proposal.json` is an optional configuration file, never a replacement for default deployment configuration. Its operator entry point requires the exact diagnostic flag, production context, private activation flags off and reviewed source/approval metadata. Importing the inactive operator does not construct a database connection or invoke a provider. No global build hook or public diagnostic endpoint is installed.

Any execution requires separate approval of exact source, SQL, configuration and command. Existing secrets remain inside the trusted runtime; do not export them, place values in arguments or commit generated approval/activation records. Readiness, protection and native rollout must be coordinated separately.

## Output and validation limits

The operator uses a public fixed reproduction input. It keeps only closed status/type buckets, presence booleans, bounded step/function/error/token counts and validator results. It does not retain text, prompt, coordinates, source URLs, opaque IDs or token values. The result must match its job binding and affect exactly one row. There is no polling, background/store mode, URL followup or automatic continuation.

Synthetic/disposable PostgreSQL tests cover immutable bindings, race/replay, cumulative accounting, disabled guards, unsafe grants, expired/future/prebound inserts and reset refusal. Fixture results do not prove actual provider completion or route/photo/Saved/packing behavior. Observe and review any real result before claiming live remediation or authorizing later native acceptance.

Revocation preserves all spent phase and original counters. Expired or used phases cannot be silently renewed.
